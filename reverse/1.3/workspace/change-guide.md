# 后续修改规范

## 修改顺序

1. 在 `patches/` 新建一个以功能命名的目录，写清目标、基线提交、涉及文件和回滚方式。
2. 先改 `decompiled` 中最小范围的业务文件，保留原有资源加载和回调顺序。
3. 对每个请求、场景切换和资源回调增加可关闭的日志；日志不要记录 token、密码或完整用户数据。
4. 运行静态检查：Lua 语法、接口字符串、资源路径和重复场景切换。
5. 记录真实设备测试步骤和结果，再生成新的 APK 分片提交。

## 不应直接做的事情

- 不要把 `lua/source` 当作文本源码编辑。
- 不要删除原有图集/骨骼加载调用来规避崩溃。
- 不要把支付成功、奖励到账或战斗胜利硬编码在客户端。
- 不要把服务端返回字段静默改名；先在 DTO/协议层做兼容映射。
- 不要用一次性全局回调处理多个异步资源；使用计数器或明确的完成状态。

## 每次修改的验收清单

- 冷启动、登录、切换后台后状态仍正确；
- 第一章第一关能完成“选关 → 初始化 → 资源加载 → 战斗 → 结算”；
- 召唤/抽奖结果能显示伙伴、奖励和确认按钮；
- 资源缺失时有日志且不阻塞核心玩法；
- 网络失败能显示错误并允许重试；
- 原 APK 基线仍可通过 `git show` 找回。

## 反编译代码的边界

这些 Lua 文件来自字节码反编译。对复杂闭包、异常分支和元表行为修改前，应同时对照 `../lua/source` 的字节码文件、调用方和运行日志；不能把反编译文本当成精确的原始源码。
